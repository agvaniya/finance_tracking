# Ledgerline

A personal finance tracker for credit cards and a checking account, with
accounts for several people on one deployment:
record balances as they change, log payments, and see what the month ahead looks
like — including warnings when scheduled auto pays would overdraw checking.

Built with Next.js (App Router), Prisma on PostgreSQL, Tailwind CSS, and
Recharts. Containerized, with Terraform for a minimal-cost AWS deployment
(Fargate + RDS).

## Features

- **Accounts** — anyone can sign up with a username and password. Each account
  sees only its own cards, balances, schedules and history; a card id belonging
  to someone else simply 404s. A forgotten password is recovered by answering
  two security questions chosen at signup, and the account menu in the header
  offers change password, delete account, and sign out. Deleting an account
  removes every record it owns.
- **Credit cards** — add any number of cards with credit limit, auto pay day,
  and an auto pay rule per card: statement (last month) balance, full balance,
  minimum payment, fixed amount, or none.
- **Balance tracking** — each card tracks *total balance* and *last month
  (statement) balance due this month*. Record a payment at any time; it updates
  the card and can optionally deduct from checking.
- **Checking account** — update the balance whenever it changes, with a reason
  ("Salary deposited", "Gift received", "Refund issued from insurance", …).
  Full history is kept for everything.
- **Recurring income** — schedule any number of salaries or other repeating
  deposits, each with its own cadence: monthly, twice a month, every two
  weeks, or weekly. Day-of-month schedules clamp to short months; fortnightly
  and weekly ones repeat from a pay date you supply. Any schedule can be
  paused without deleting its history.
- **Scheduled expenses** — rent, a car lease, utilities: the same cadences,
  flowing the other way. A bill that varies can be marked as an estimate, and
  when the real one arrives you correct that single due date from the
  **Upcoming bills** list without touching the schedule. Later months keep the
  estimate; entering 0 means it will not be charged that time.
- **Predictions** — the checking balance is projected forward from scheduled
  income and bills, this month's remaining card payments, estimated later
  statements, and the residual spending your history does not otherwise
  explain. You get: expected end-of-month checking balance, the lowest projected point,
  payoff headroom (what you could still pay this month while keeping a $500
  buffer), and warnings when an auto pay would overdraw the account.
- **Dashboard** — balance trend lines (90 days), a donut of debt distribution
  across cards, a monthly calendar marking balance updates, payments, payoff
  moments, and approaching auto pay dates, plus recent activity.

## Getting started (local)

```bash
cp .env.example .env            # then set SESSION_SECRET
npm install
docker compose up -d db         # Postgres on localhost:55432
npx prisma migrate dev
npm run db:seed                 # optional: ~3.5 months of demo data
npm run dev
```

Open http://localhost:3000 and create an account, or sign in to the seeded demo
account as `demo` with password `demo-password-1` (override with `SEED_USERNAME`
and `SEED_PASSWORD`). Its security answers are "Rex" and "Boston".

The seed is skipped automatically if the database already has data. To start
clean: `docker compose down -v && docker compose up -d db && npx prisma migrate dev`.

## Running the whole stack in Docker

```bash
cp .env.example .env            # set SESSION_SECRET
docker compose up --build
```

This runs the app and Postgres together. The app container applies pending
migrations on boot (`prisma migrate deploy`, with retries while the database
finishes starting), then serves on http://localhost:3000. Data lives in the
`db-data` volume.

The image is a multi-stage build on `node:22-alpine` running Next.js standalone
output as a non-root user. Configuration is entirely env-driven:
`DATABASE_URL`, `SESSION_SECRET`, `PORT`, and `SESSION_COOKIE_SECURE`.

> `SESSION_COOKIE_SECURE` must be `false` when the app is served over plain
> HTTP — browsers discard a `Secure` cookie on an insecure origin, which would
> make login appear to silently fail. It defaults to secure in production and
> is set automatically by both compose and Terraform.

## Deploying to AWS (Fargate + RDS)

```bash
./scripts/deploy.sh             # provision, build, push, roll out
./scripts/status.sh             # where it is running, and how it is doing
./scripts/destroy.sh            # tear it all down
```

`deploy.sh` needs the Terraform CLI, Docker, and configured AWS credentials. It
creates the ECR repository first, builds and pushes the image for the task's
architecture, applies the rest of the stack, waits for the service to reach a
steady state, and prints the URL. The session secret and database password are generated by Terraform and stored
in SSM Parameter Store, never written to the repo; application accounts are
created through the app's own signup page.

Re-deploying after a code change is the same command. Each run tags the image
with a UTC timestamp, so a new task definition revision rolls out and you can
roll back by pointing `image_tag` at an older tag.

### What gets created

All of it lives in `infra/terraform/`:

Everything lands in **us-west-1**.

| Resource | Choice made for cost |
| --- | --- |
| VPC, 2 public subnets, internet gateway | No NAT gateway (~$32/mo saved) and no interface endpoints (~$7/mo each). The task gets a public IP; RDS has none. |
| ECS Fargate service, 1 task | 0.25 vCPU / 512 MB on ARM64 (Graviton, ~20% cheaper), running on **Fargate Spot** (~70% cheaper). |
| RDS PostgreSQL 16 | `db.t4g.micro`, single-AZ, **5 GB gp2**, 1-day backups, no Performance Insights or enhanced monitoring. |
| Secrets | SSM Parameter Store standard parameters (free) rather than Secrets Manager (~$0.40 per secret per month). |
| Logs | CloudWatch group with 7-day retention; Container Insights disabled. |
| ECR | Lifecycle policy keeping only the 5 most recent images. |
| TLS and DNS | No load balancer. Caddy terminates TLS inside the task, and a Lambda repoints the A record when the task moves — see below. |
| EFS (certificate storage) | A few hundred KB, well under a cent a month. |
| Lambda + EventBridge | AWS-sourced events are free; the function runs a few times a month. |

Rough monthly cost: **about $18**, almost entirely RDS (~$12 for the instance
plus well under $1 for 5 GB) and the public IPv4 address (~$3.60), with Fargate
Spot around $2–3. A new AWS account's free tier covers the RDS instance for
12 months.

> **Why 5 GB is gp2, not gp3.** RDS will not create a gp3 volume smaller than
> 20 GB, while gp2 goes down to 5 GB — so meeting a 5 GB target requires gp2.
> At that size gp2 gives a 100 IOPS baseline with burst credits, which is
> plenty for a single-user app. Terraform rejects the invalid combination
> (`gp3` under 20 GB) rather than letting the apply fail.

### Domain and TLS

The app is served at **https://finance.agvaniya.com**, with no load balancer in
the path. Three pieces make that work, selected by `tls_mode = "letsencrypt"`:

**Caddy terminates TLS inside the task.** The image bundles Caddy built with
the `caddy-dns/route53` plugin. It obtains a Let's Encrypt certificate using
the **DNS-01** challenge — answered by writing a TXT record into the hosted
zone with the task's own IAM role — and renews automatically well before
expiry. HTTP-01 would be the obvious alternative but it races the DNS update
on every task replacement, whereas DNS-01 needs no inbound connectivity at
all. Caddy owns ports 80 and 443, redirects 80 to 443, and proxies to Next.js
on the loopback; the application port is never exposed.

**Certificates persist on EFS.** This matters more than it looks. Fargate's
task storage dies with the task, so without a durable volume Caddy would ask
for a brand-new certificate every replacement — and Let's Encrypt permits only
**5 identical certificates per week**. A few Spot reclamations would exhaust
that and leave the site without a usable certificate for days. The EFS volume
holds the ACME account key and certificate so a restart reuses them.

**A Lambda keeps DNS pointed at the task.** An EventBridge rule fires on ECS
task state changes; the function resolves the task's ENI to its public IP and
UPSERTs the A record with a 60-second TTL. Terraform creates the record with a
placeholder address and `ignore_changes`, so it owns the record's lifecycle
without fighting the Lambda over its value.

The cost of avoiding the load balancer is a **gap on every task replacement**:
the new task has a new IP, and clients keep the old one until the TTL expires.
Expect roughly one to two minutes of unavailability after a deploy or a Spot
reclamation. If that becomes annoying, `use_fargate_spot = false` removes the
unplanned half, and `tls_mode = "alb"` removes it entirely for ~$17/month.

> While experimenting, set `acme_staging = true`. Staging certificates are not
> trusted by browsers, but the real CA's 5-per-week limit is easy to burn
> through during setup and there is no way to reset it.

Other modes: `tls_mode = "alb"` provisions an ACM certificate on an
Application Load Balancer with an alias record (stable address, seamless
replacements). `tls_mode = "none"` serves plain HTTP on the task's public IP
with no domain — in which case set `allowed_cidrs = ["YOUR.IP/32"]`, since the
password and session cookie would otherwise cross the internet in the clear.

### Operating it

```bash
./scripts/status.sh --logs                       # state, address, recent logs
./scripts/deploy.sh --skip-build                 # redeploy the current image
aws ecs execute-command --cluster ledgerline \
  --task <task-id> --container app \
  --interactive --command /bin/sh                # shell into the running task
```

To run `psql` or `pg_dump` from your laptop, add your IP to
`db_public_access_cidrs` and apply; the connection string is
`terraform -chdir=infra/terraform output -raw database_url`.

Terraform state is a local file by default. If more than one person deploys,
uncomment the S3 backend block in `infra/terraform/versions.tf`.

## Switching databases again

The app never talks to Postgres directly: all access goes through Prisma, money
is stored as integer cents, and there is no provider-specific SQL. Moving to
MySQL, or back to SQLite for a local-only setup, is three steps:

1. Change `provider` in the `datasource` block of `prisma/schema.prisma`.
2. Point `DATABASE_URL` at the new database.
3. Recreate migrations, which are provider-specific: delete
   `prisma/migrations/` and run `npx prisma migrate dev --name init`.

Nothing in `src/` changes, and the container entrypoint's `migrate deploy`
works the same against any of them.

## How predictions work

The forecast starts from the latest recorded checking balance and replays the
money we know is going to move, then adds a small history-derived residual.

- **Scheduled income** lands on each pay date; **scheduled bills** leave on
  each due date (at the corrected amount where you have entered one).
- **This month's card payments** are what is still due after the payments
  already recorded this month. Recording a payment reduces the amount due,
  never below $0. A card with auto pay withdraws on its configured day
  (statement balance, full balance, minimum, or fixed); a card paid by hand
  owes its remaining statement balance on the day it is usually paid, or at
  month end.
- **Later card payments** are estimated. Each card's typical monthly charges
  are measured from its history (`balance change + payments recorded` over up
  to 90 days, falling back to the average of recent statement balances). The
  spending already on the card above its statement, plus a proportional share
  of a typical month, becomes next month's statement; after that each month
  adds a typical month of charges. The card's auto pay rule is applied to that
  estimated statement; a card paid by hand uses its typical monthly payment.
  These rows are marked "est" on the dashboard.
- **Other spending**: whatever change in the recorded checking balance is
  *not* explained by the scheduled income, bills and card payments in the
  same window becomes a per-day residual (cash withdrawals, transfers,
  anything that bypasses the cards). It needs at least 14 days of history;
  with less, the forecast is the explicit events only.

> **Why the residual subtracts card payments.** Past salaries, rent and card
> payments all moved the recorded balance, so they are inside the observed
> drift. Projecting them forward on top of the raw drift would count the same
> money twice — once in the drift and again on the day it fires — which is
> what made earlier forecasts dive. Record card payments as payments (not
> just as a lower card balance) so they can be taken back out of the history.
> The "Other spending per day" figure on the Checking page is the number to
> sanity-check if a forecast looks off; a schedule entered for something
> genuinely new, with no matching history, skews it until history accumulates.

- **Warnings**: a card payment that leaves checking below $0 is flagged as an
  overdraft; below the $500 safety buffer as "tight". Both appear on the
  dashboard banner, the projection chart, and the calendar.
- **Payoff headroom**: the month's lowest projected balance minus the buffer —
  what you could safely pay toward cards beyond what's already planned.

Predictions only know what you record: the more regularly balances and
payments are logged, the better the forecast.

## Versioning

The version lives in `package.json` (`"version"`) and is shown in the account
menu and in the bottom-right corner of the sign-in screen. It follows
`major.feature.patch`:

- **patch** (last part): bug fixes and small builds.
- **feature** (middle): a major feature.
- **major** (first): only bumped by explicit decision.

Bump it in `package.json` (and `package-lock.json`) as part of the change
that ships it.

## Project layout

```

                       prediction engine, calendar events, chart sampling
```
